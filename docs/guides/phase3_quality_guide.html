Why evaluate in stages

A wrong answer can come from any of nine places: parsing, chunking, either retriever, fusion, reranking, the context budget, the LLM, or the citation step. One end-to-end score says something is wrong; per-stage scores say where. Phase 2's traces already record the hits of every stage, so Phase 3 can score each one from a single run.

Chapter 2 · Foundations

What to measure

For an interview assistant, quality means: the right candidates surface, every claim is true to the resume, nothing is invented, unfair cues have no effect, and it answers fast enough to use in a real interview.

The metric map

LevelQuestion it answersMetricsNeeds
RetrievalDid the evidence reach the top of the list?Recall@k, Precision@k, MRR, nDCG@k, candidate recall@kRelevant chunks per question
RoutingWas the question understood and the filter exact?Intent accuracy, filter precision/recall, exact-set matchExpected intent and candidate sets
AnswersIs the answer true to the evidence, relevant and complete?Citation validity/precision, faithfulness, relevance, correctness, refusal accuracyReference answers; judge or humans
Fairness & robustnessDo irrelevant attributes or injected text change outcomes?Rank stability under swaps, injection resistanceCounterfactual and adversarial resumes
SystemIs it fast and cheap enough?p50/p95 latency per stage, time to first token, tokens per answerTraces

Offline versus online

Offline (this phase)

Fixed golden set, repeatable, runs on the laptop, compares configurations fairly. Limited to the questions you thought of.

Online (production, later)

Real interviewer questions, thumbs up/down, citation clicks, edits to answers. Finds what the golden set missed; feeds new golden questions back.

Order of work

  1. Retrieval first: no LLM needed, fast, and most failures start here.
  2. Routing and structured answers: deterministic and cheap.
  3. Answers: slow (LLM generation plus judging), so run on the best retrieval config only.
  4. Fairness, robustness and system metrics on the chosen config.
Chapter 3 · Data

Building the golden dataset

Every metric is only as good as the questions and labels behind it. The golden set is the most valuable artefact of Phase 3, and the one most often done badly.

Sources of questions

SourceHowStrengthWeakness
Generated from ground truth chosenPhase 1 fixture YAML → "Who has a CKA?", "Who has 5+ years of Go?"Free, exact answersTemplate-like phrasing; structured intents only
Hand-written chosenRead fixtures, write depth / compare / JD / gaps questionsRealistic, hardSlow; author bias
LLM-drafted, human-reviewed chosenLLM proposes questions per chunk; you keep, fix or dropVariety at low costQuestions copy chunk wording (too easy) unless reviewed
Synthetic test-set generatorsRAGAS / DeepEval test-set generationFast, many typesNeeds a strong LLM; same "too easy" risk
Production logsReal questions from traces, labelled laterThe real distributionOnly after launch

Label by evidence, not by chunk id

Chunk ids change whenever budgets or the chunker change (Phase 1 recomputes budgets as the corpus grows). Labels tied to ids would silently go stale. Instead, each question stores evidence quotes; at eval time a chunk is relevant if it contains the quote.

- id: q017
  split: dev
  intent: depth
  question: "Who has led a migration to Kubernetes, and where?"
  expected_candidates: [single_col_backend]
  evidence:
    - candidate: single_col_backend
      quote: "Led migration of 40 services to Kubernetes"
      grade: 2            # 2 = answers it, 1 = partially relevant
  reference_answer: "Priya Raman led the migration of 40 services to Kubernetes on EKS at Northwind Payments."
  answerable: true

Resolution normalises whitespace and case and falls back to fuzzy matching for quotes split across a chunk boundary. A quote that matches no chunk is itself a finding: the evidence was lost in parsing or chunking.

Size and split

  • 80–120 questions; at least 8 per intent.
  • Dev (60%) for tuning; test (40%) touched once, for the final report. Tuning on the test split makes the final numbers optimistic.
  • Split by resume, not by question, where possible: questions about the same resume in both splits leak information.

Chosen for this use case

  • Auto-generated structured questions + hand-written hard ones + reviewed LLM drafts.
  • Evidence quotes with graded relevance, resolved to chunks at eval time.
  • Dev/test split, mostly by resume; fictional data only in the repository.

Coverage, negatives and adversarial questions

A golden set of easy questions produces high scores and false confidence. Plan coverage deliberately: every intent, every difficulty, and questions that should get "no".

Hard questions, with examples

  • Paraphrase: "Who has kept payment systems reliable under load?" for "Designed an idempotent payment retry service handling 1.2M transactions/day".
  • Multi-hop: "Among candidates with a CKA, who has also worked with Kafka in production?"
  • Temporal: "Who used Python most recently?" (needs dates, not just mentions).
  • Claimed vs used: "Who has actually used Terraform in a job, not just listed it?"

Negatives

Questions whose correct answer is "nobody" or "not mentioned": "Who has Rust experience?" when no fixture has Rust. They measure the most dangerous failure for this use case, a confident answer the resume does not support. Mark them answerable: false.

Adversarial resumes

  • An injection line hidden in a resume (Phase 2 fixture).
  • A keyword-stuffed Skills section with 80 technologies and no matching experience.
  • Counterfactual copies of a resume that differ only in name, pronouns or nationality cues (chapter 9).
  • Noisy parse variants: shuffled sidebar order, OCR-style character errors.
Chapter 5 · Metrics

Retrieval metrics

Retrieval metrics compare a ranked list of chunks with the set of relevant chunks. Each metric answers a slightly different question; together they show whether evidence is found and how high it ranks.

The metrics

\[\text{Precision@}k = \frac{|\text{relevant} \cap \text{top}_k|}{k} \qquad \text{Recall@}k = \frac{|\text{relevant} \cap \text{top}_k|}{|\text{relevant}|}\]
\[\text{MRR} = \frac{1}{|Q|}\sum_{q} \frac{1}{\text{rank of first relevant}} \qquad \text{nDCG@}k = \frac{\sum_{i=1}^{k} \frac{2^{g_i}-1}{\log_2(i+1)}}{\text{IDCG@}k}\]
MetricAnswersUse here
Recall@kDid the evidence make it into the top k at all?Main retrieval metric: missing evidence cannot be recovered later
Precision@kHow much of the top k is useful?Context budget efficiency
MRRHow high is the first relevant hit?Lookup questions with one answer
nDCG@kAre the most relevant hits (grade 2) above partial ones (grade 1)?Uses graded labels; best single ranking metric
MAPAverage precision over all relevant positionsMany relevant chunks per question
Hit rate@kAt least one relevant in top k (per question)Simple sanity metric
Candidate recall@kDid the expected candidates appear in the top k candidates?The metric interviewers feel most

A wrong structured answer is almost always an extraction problem (Phase 1 metadata) or an entity-parsing problem (Phase 2 rules), not a SQL problem. Each failure is traced to one of the two.

Chapter 7 · Metrics

Answer (generation) metrics

Good retrieval does not guarantee a good answer. The model can ignore evidence, add facts, cite the wrong passage, or answer when it should refuse.

Families of methods

FamilyExamplesStrengthWeakness
Deterministic checks firstCitation validity, number support, refusal detection, required candidates mentionedExact, free, explainableCannot judge meaning
Lexical overlapExact match, token F1, ROUGE, BLEUCheapPenalise correct paraphrases; poor for free-form answers
Embedding similarityCosine to reference, BERTScoreTolerates paraphraseHigh scores for fluent but wrong answers
LLM-as-judge chosenRubric scoring of faithfulness, relevance, completenessJudges meaningBiased and noisy; must be calibrated (chapter 8)
Framework metricsRAGAS (faithfulness, answer relevancy, context precision/recall), DeepEval, TruLens, Phoenix evalsReady-madeDefault prompts assume a strong judge; check on small local models
Human evaluationReviewer rates answersGround truth for meaningSlow; used to calibrate the judge

The answer metrics we report

MetricDefinitionHow
Citation validityCited ids exist in the contextCode (Phase 2 check)
Citation precisionCited passage supports the sentenceJudge per (sentence, passage)
Citation recallFactual sentences that carry a citationCode + judge for "is this a factual claim"
FaithfulnessShare of claims supported by the contextJudge: split into claims, verify each
Answer relevanceAnswers the question askedJudge, 1–5 rubric
CorrectnessAgrees with the reference answer; expected candidates namedCode (candidates) + judge (content)
Refusal accuracyRefuses when answerable: false, answers otherwiseCode (refusal phrase / no claims) + judge

Faithfulness, step by step

  1. Split the answer into atomic claims: "C12 led a migration", "of 40 microservices", "at PayNova", "cutting cost by 32%".
  2. For each claim, ask the judge: is it supported by the context passages? (yes / no / partly)
  3. Faithfulness = supported claims / all claims.

Faithfulness is measured against the context, not the reference answer: an answer can be faithful but incomplete, or correct by luck but unfaithful. Report both.

Chapter 8 · Metrics

The LLM judge and its calibration

An LLM judge scales meaning-level evaluation, but it is a measuring instrument with its own errors. Before trusting its numbers, measure how often it agrees with a human.

Known judge biases

BiasEffectMitigation
Self-preferenceRates answers from its own model family higherJudge from a different family (llama3.1 judging qwen2.5)
VerbosityPrefers longer answersRubric rewards precision; length-matched comparisons
PositionIn pairwise comparisons, prefers the first (or second) answerEvaluate both orders; count only consistent wins
LeniencySmall models say "supported" too easilyBinary questions per claim; examples of "not supported"
Format sensitivityScores change with prompt wordingFixed, versioned judge prompts; temperature 0

Judge designs

  • Pointwise rubric chosen: score one answer on a 1–5 scale with anchored descriptions, or binary per claim. Simple and comparable across runs.
  • Pairwise: "which answer is better?" Good for comparing two prompt versions; needs both orders.
  • Reference-guided: judge sees the reference answer. Better for correctness; can over-penalise valid alternatives.

Calibration with Cohen's kappa

Label 30 answers yourself (pass / fail per metric), run the judge on the same answers, and compare. Raw agreement overstates quality when most answers pass; kappa corrects for agreement expected by chance:

\[\kappa = \frac{p_o - p_e}{1 - p_e}\]

\(p_o\) is observed agreement; \(p_e\) is the agreement two raters would reach by chance given how often each says "pass". Common reading: below 0.4 poor, 0.4–0.6 moderate, 0.6–0.8 substantial, above 0.8 near perfect.

Chosen for this use case

  • Pointwise rubric judge, temperature 0, versioned prompts, different model family from the generator.
  • Claim-level binary verification for faithfulness and citation precision.
  • Calibrated on 30 human labels; a judge metric with kappa below 0.6 is reported as untrusted, not used for decisions.
  • Judge outputs cached by (prompt hash, model), so re-running reports is free.
Chapter 9 · Metrics

Fairness and robustness tests

Hiring is a high-stakes domain. The assistant should behave the same when only irrelevant attributes change, and should not be steerable by text the candidate planted.

Counterfactual fairness tests

Make copies of a resume that differ in one attribute only, index them, and check that outcomes do not change.

SwapExampleCheck
Name (gender / ethnicity cues)Priya Raman ↔ Peter Ross ↔ Wei ChenRank position and coverage scores identical
Pronouns / gendered words"she led" ↔ "he led"; "chairwoman" ↔ "chair"Same
Nationality / locationPune ↔ AustinSame unless the JD requires location
Career gap reason"parental leave" vs no reasonGap is reported neutrally; ranking unaffected
University prestigeTwo universities of different reputationRanking unaffected (education is not a JD requirement)

Rankings are computed in code from evidence (Phase 2), so they should be exactly stable. Summaries are generated by the LLM, so compare them with the judge: "do these two summaries differ in substance?" Report the share of pairs judged equivalent.

Robustness tests

TestPass condition
Injection line in a resumeWarning raised; ranking unchanged; line absent from prompts
Keyword stuffingCandidate not ranked above candidates with used evidence
Question paraphrasesSame top candidates for 3 paraphrases of the same question
Noisy parse (OCR-like errors)Recall drop within a stated tolerance
Typos in questions"kubernets", "pyhton" still route and retrieve
These tests support, not certify.

Passing them shows the system is not obviously biased on the attributes tested. It does not make the system compliant with hiring regulations; that needs process, documentation and legal review.

System metrics

An accurate answer that takes a minute is not useful mid-interview. Phase 2's traces already time every stage; Phase 3 summarises them.

What to report

MetricWhy percentiles
Latency per stage, p50 / p95Averages hide the slow cases interviewers remember; p95 shows them
Time to first tokenWhat the interviewer feels with streaming
Total answer timeFor non-streamed views (Match explanations)
Prompt and answer tokensDrives latency now, cost later with paid models
LLM fallback rateEach fallback adds seconds
Index build time per resume, index memoryUpload experience; laptop limits

Cost model for the paid swap

When an LLM, embedder or reranker moves to a paid API, cost per question is roughly

\[\text{cost} \approx T_{\text{in}}\cdot p_{\text{in}} + T_{\text{out}}\cdot p_{\text{out}} + n_{\text{rerank}}\cdot p_{\text{rerank}} + T_{\text{query}}\cdot p_{\text{embed}}\]

with token counts taken from traces and prices from the provider's current price list. Measuring \(T_{\text{in}}\) and \(T_{\text{out}}\) now makes that estimate a lookup later.

Chapter 11 · Experiments

Experiments and statistical significance

With 60 dev questions, one question is 1.7 percentage points. Many "improvements" are noise. Compare configurations on the same questions and attach confidence intervals.

What to vary

FactorValuesNeeds LLM?
Embedding modelbge-small, nomic-embed-textNo (re-index)
Chunk budget p_high80, 90, 95No (re-chunk + re-index)
Fusion weights1:1, 1:0.5, 0.5:1No
Rerankeroff, MiniLM-L6, bge-reranker-baseNo
k after rerank8, 12, 20Yes (affects context)
LLMqwen2.5:3b, qwen2.5:7bYes
Prompt versionv1, v2Yes

Designs

  • Full grid: every combination. 2 × 3 × 3 × 3 = 54 retrieval runs; fine without an LLM, impossible with one on a laptop.
  • One factor at a time around the best chosen: start from the current config, vary one factor, keep the winner, move on. Misses interactions but is affordable.
  • Retrieval first: fix retrieval with cheap metrics, then tune generation on that retrieval.

Paired comparison and the bootstrap

Both configurations answer the same questions, so compare them per question. What matters is the questions where they disagree. The bootstrap resamples questions with replacement thousands of times and recomputes the difference; the middle 95% of those differences is the confidence interval. If it includes zero, the improvement is not established.

Chosen for this use case

  • Retrieval factors first, one at a time around the best; then generation factors.
  • Paired bootstrap (2,000 resamples, fixed seed) for every reported difference.
  • A change is adopted only if its CI excludes zero on dev, then confirmed once on test.
Chapter 12 · Experiments

Error analysis: find the stage that failed

Metrics say how often; error analysis says why. Walk each failed question through the pipeline until the evidence disappears. The first stage where it is lost is the one to fix.

Failure taxonomy

StageSymptomTypical fix
ParsingEvidence quote not in the MarkdownRouter rules, column detection, OCR fallback
ChunkingQuote split across chunks, or merged into an unrelated chunkBudgets, entry detection
Dense retrievalRelevant chunk not in dense top-50Embedding model, prefix, enrichment
Keyword retrievalExact term query missedTokenizer, aliases
FusionIn a retriever's top list but not in fused top-30Weights, k
RerankingIn fused top-30, dropped after rerankReranker choice, input text, switch off
ContextRetrieved but dropped by the budgetBudget, per-candidate cap, parent expansion
GenerationIn context, answer ignores or distorts itPrompt, model, temperature
CitationCorrect claim, wrong or missing citationPrompt examples, citation format
RoutingWrong intent or entitiesRules, fallback prompt

Failure diagnosis

Answer each question about one failed golden question, using its trace and the Inspect page. The walk stops at the first stage that lost the evidence.

Doing it in bulk

Because every stage's hits are in the trace, the walk can be automated: for each failed question, record the first stage where the relevant chunk is absent. A table of "failures by first lost stage" tells you where the next improvement should go.

Chapter 13 · Experiments

Tracking, regression gate and exit

An evaluation is only useful if results are comparable over time and a bad change cannot slip in unnoticed.

Tracking runs

OptionFit
JSONL results + Markdown report per run chosenNo services; diffable; Streamlit Eval page reads them
MLflow (local)Run comparison UI and artefacts; one extra process
Langfuse / Arize Phoenix (self-hosted)Tracing + eval datasets + judge runs; best for production
Hosted eval platformsTeam features; data leaves the machine

Every run records: config (full, after overrides), config hash, git commit, Phase 1 index_version, prompt and judge versions, golden-set version, seed, and per-question results.

The regression gate

# eval/thresholds.yaml
absolute:
  recall_at_10: 0.90
  candidate_recall_at_5: 0.90
  citation_validity: 1.00
  refusal_accuracy: 0.90
regression:               # versus eval/baselines/accepted.json
  max_drop:
    recall_at_10: 0.02
    mrr: 0.03
    faithfulness: 0.03
  • In pytest (every change): a smoke eval of 10 questions with fakes checks the evaluation code and catches gross breakage.
  • Locally with real models (before merging changes that touch retrieval or prompts): scripts/run_eval.py --split dev --gate fails with the metric that dropped.
  • Accepting a new config writes a new baseline; the old one stays in history.

Production monitoring (next steps)

  • Traces to a self-hosted tracer (Langfuse or Phoenix) via OpenTelemetry.
  • Interviewer feedback (thumbs, edits, citation clicks) stored with the trace.
  • Weekly sample of real questions labelled and added to the golden set.
  • Drift watch: intent mix, fallback rate, refusal rate, latency p95.
