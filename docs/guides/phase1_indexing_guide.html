The Phase 1 map

Indexing turns a pile of resume PDFs into three searchable stores: vectors for meaning, a keyword index for exact skills, and a metadata database for facts. Everything the interviewer later asks is answered from these three.

What we are building

An interviewer opens a role ("Senior Backend Engineer, Payments"), sees 60 submitted resumes, and asks questions like "Who has run Kubernetes in production?", "Summarise Arjun's payments experience" or "Which candidates have more than 5 years of Go?". The assistant answers with citations to the exact resume lines.

Phase 1 is everything that happens before any question is asked. It runs when resumes are uploaded. Its job is to make every fact in every resume findable, attributable to one candidate, and citable.

The contract Phase 1 hands to Phase 2

Phase 2 (retrieval) will not care which parser or chunker you used. It only needs these outputs, with these guarantees. Fix this contract early and you can change everything behind it later.

OutputContentsGuarantee
Vector indexOne vector per chunk, keyed by chunk_idAll vectors from one model and version; normalised
Keyword indexBM25 over the same chunksSame chunk_ids as the vector index

Index manifestParser, chunker config, embedding model, created timePhase 2 refuses to query with a different embedding model

Why most of the effort is here

If the right passage never reaches the LLM, nothing in Phase 2 can recover it. For resumes this is especially sharp. Resumes are short, dense, visually designed documents. A two-column template parsed in the wrong reading order mixes skills from the sidebar into job descriptions. A chunk that says "Led migration of 40 services to EKS" without the company name cannot answer "where did they do that?". Most of the quality of the final assistant is decided in this phase.

Chapter 2 · Foundations

Know your corpus and your questions

The right indexing design comes from two facts: what resumes look like, and what interviewers ask of them. Get these straight and most decisions make themselves.

What resumes look like

PropertyTypical valueConsequence for indexing
Length1–3 pages, 400–1,500 tokensA whole resume nearly fits in one embedding window, but one vector for all of it is too blurred to match specific skills
StructureStrong, conventional sections: Summary, Skills, Experience, Education, Projects, CertificationsSection-aware chunking is natural and free
Heading namesVary widely: "Work History", "Employment", "Professional Experience"Need a synonym map to canonical section names
LayoutTemplates with two columns, sidebars, tables, icons, skill barsNaive text extraction scrambles reading order; parsing is the riskiest step
VocabularyKeyword-dense: tool and product names, acronyms (K8s, EKS, CKA)Exact keyword search (BM25) matters as much as semantic search
FactsDates, companies, titles, degrees, certificationsMany questions are structured filters, not semantic search
Personal dataName, email, phone, address, sometimes photo and agePII handling and bias controls are required, not optional
Volume10–500 resumes per roleTiny for a vector index: exact (flat) search is fast enough

What interviewers ask

Classify the questions first. Different question types need different stores, which is why Phase 1 builds three of them.

Question typeExampleBest served by
Skill lookup"Who knows Terraform?"BM25 + skill table
Experience depth"Who has led a large migration to Kubernetes?"Dense vectors over experience entries
Structured filter"Candidates with 5+ years and a CKA"Metadata DB (SQL), no vectors at all
Single-candidate summary"Summarise Arjun's payments work"Metadata filter on candidate, then all their chunks
Comparison"Compare the top three on system design"Retrieval per candidate, then aggregate (Phase 2)
Gaps and red flags"Any unexplained career gaps?"Experience date table (computed at indexing time)
Interview prep"Suggest questions to probe her Kafka claim"Dense retrieval of the specific claim + LLM
Key insight.

Roughly half of interviewer questions are about facts that can be extracted once and stored as fields: years of experience, skills, certifications, companies, dates. Answering those with vector search is slower and less reliable than a SQL filter. That is why metadata extraction (chapter 7) gets as much attention as embeddings.

Corpus scope: per role

Every resume belongs to a role (a job opening). Interviewers almost always search within one role. Two designs are possible:

  • One index per role. Simple isolation; but a candidate who applies to two roles is indexed twice, and cross-role search ("anyone in our pool with Rust?") needs fan-out.
  • One shared index, role_id as a metadata filter chosen. One copy of each resume, filter at query time, cross-role search is free. Requires the vector store to support metadata filtering, which every option in chapter 13 does.

What this means for Phase 1

  • Parse carefully: layout is the main risk.
  • Keep structure: sections and job entries are the natural chunk units.
  • Extract facts into fields, not only into vectors.
  • Build BM25 next to dense vectors from day one.
  • Scale is small: favour simplicity and exactness over approximate indexes.
Chapter 3 · Ingestion

Upload and intake

Intake is unglamorous, but it decides whether re-uploads create duplicates, whether a crash loses work, and whether you can delete a candidate's data on request.

What happens on upload

  1. Validate: file type by magic bytes (not just the extension), size limit (for example 10 MB), page limit (for example 10 pages), reject encrypted PDFs with a clear message.
  2. Hash: sha256 of the raw bytes. If this hash already exists for this role, skip; the file is already indexed.
  3. Store the raw file under data/raw/{role_id}/{sha256}.pdf. You will re-parse it whenever the parser improves.
  4. Create a document record with status uploaded, then move it through parsed → chunked → embedded → indexed or failed with an error message.

Methods for running the pipeline

MethodHowGood forWeak at
Synchronous in the requestUpload endpoint parses, chunks and embeds before respondingDemos, one file at a timeA 60-resume batch blocks for minutes; a crash loses the batch
Background job + status table chosenEndpoint stores files and returns; a worker thread or process picks up uploaded documentsBatches, retries, progress barsSlightly more code
Task queue (Celery / RQ / Dramatiq + Redis)Each document is a queued task, workers scale horizontallyProduction, many concurrent uploadsExtra infrastructure
Managed pipeline (cloud functions, Step Functions)Event on file upload to object storage triggers processingLarge-scale productionVendor lock-in, harder local testing

The status table is the same in all four, so you can start with a simple background worker and move to a task queue later without changing the data model.

Duplicates are subtler than they look

CaseDetect withAction
Same file uploaded twiceIdentical sha256Skip silently
Same candidate, re-exported PDF (bytes differ)Hash of normalised extracted textSkip, link to existing
Same candidate, updated resumeSame email or phone in extracted metadataKeep newest as active version, archive the old one
Near-identical resumes from different people (templates, agencies)MinHash / Jaccard on shingles above ~0.9Flag for review, never auto-merge

Multiple files per candidate

Some candidates submit a resume plus a cover letter or portfolio. Model this as candidate 1 → n documents, each with a doc_type. Chunks carry both candidate_id and doc_id. Retrieval can then weight resume chunks above cover-letter chunks, and citations name the right file.

Personal data from the first byte.

Resumes are personal data under GDPR and India's DPDP Act 2023. Decide now: retention period (for example delete 6 months after the role closes), who can see raw files, and a delete path that removes the raw file, the DB rows, the vectors and the BM25 entries together (chapter 14).

Chosen for this use case

  • Upload endpoint validates, hashes, stores, returns immediately.
  • Background worker processes documents through a status table; failed documents keep their error and can be retried.
  • Duplicate check on raw hash and normalised-text hash; same-candidate detection by email after metadata extraction.
  • Switch to Celery/RQ when more than one worker process is needed.

Parsing PDFs: libraries, OCR and vision models

A PDF is a set of glyphs placed at coordinates, not a document with paragraphs. Parsing reconstructs reading order and structure. For resumes, with their designed layouts, this is the step most likely to go wrong silently.

The four kinds of resume PDF

KindHow to recognise itMain risk
Digital, single columnText layer present, text spans full page widthLow: headers and bullets
Digital, two column / sidebarText layer present, two clusters of x-coordinatesReading order: sidebar text interleaved with main column
Scanned or image-onlyNo text layer, or fewer than ~50 characters per pageNeeds OCR; errors in dates and numbers
Designed (Canva, infographic)Icons, skill bars, text inside shapesInformation exists only visually (a 4/5 skill bar has no text)

What goes wrong: a two-column example

Naive extraction (line by line across the page) 
SKILLS            Senior Backend Engineer, PayNova
Go, Python        Led migration of 40 microservices
Kubernetes        from EC2 to EKS, cutting infra
Terraform         cost by 32%.

Becomes: "SKILLS Senior Backend Engineer, PayNova Go, Python Led migration of 40 microservices Kubernetes from EC2 to EKS…". Skills and job text are fused; section detection fails.

Layout-aware extraction 
## Skills
Go, Python, Kubernetes, Terraform

## Experience
### Senior Backend Engineer, PayNova
- Led migration of 40 microservices
  from EC2 to EKS, cutting infra
  cost by 32%.

Every method, compared

1. Plain text extractors

Read the text layer in content-stream order. pypdf, pdfminer.six. Fast and dependency-light, but reading order follows how the PDF was written, which for designed templates is often wrong. No structure: headings come out as plain lines.

2. Layout-aware libraries

Use glyph coordinates, font sizes and blocks. PyMuPDF (fitz) gives blocks with bounding boxes and font info; pymupdf4llm turns that into Markdown, inferring headings from font size and handling multi-column pages reasonably. pdfplumber gives character-level access and strong table extraction. Fast (milliseconds per page), CPU-only, no models.

3. ML document converters

Run a layout-detection model over each page image to find titles, paragraphs, tables, lists and columns, then assemble text in reading order. Docling (IBM, MIT licence) with its layout model and TableFormer, exporting Markdown or JSON; Marker (check its licence for commercial use); MinerU; Unstructured (hi_res strategy). Much better on two-column and table layouts; seconds per page on CPU.

4. OCR engines

For scanned or image-only pages: Tesseract (classic, CPU, good on clean scans), EasyOCR, PaddleOCR, docTR, RapidOCR. Docling and Unstructured can call these for you. OCR produces text without structure, so it is usually wrapped inside a layout pipeline.

5. Vision-language models (VLM)

Give the page image to a multimodal model and ask for Markdown. Open source: Qwen2.5-VL (available in Ollama), olmOCR, granite-docling/SmolDocling (small document-specific models). They read designed layouts, icons and skill bars the way a human does. Costs: GPU or slow CPU inference, and hallucination risk: a VLM can "correct" a date or invent a word. Use as a fallback, not the default.

6. Paid parsing APIs

General: Azure AI Document Intelligence, AWS Textract, Google Document AI, LlamaParse, Reducto, Mistral OCR. Resume-specific parsers: Affinda, Textkernel, RChilli. Resume parsers return structured JSON directly (name, jobs, skills), which also covers chapter 7. They cost per page and send candidate PII to a third party, which needs a data processing agreement.

Routing: use the cheap parser when it is safe

No single parser is best for every file. A router inspects each PDF cheaply and sends it to the right parser, then checks the result and escalates if it looks bad.

inspect(pdf):
    chars_per_page   = len(text_layer) / pages
    columns          = cluster x-start of text blocks (1 or 2 clusters)
    image_coverage   = image area / page area
route:
    docx                          → Docling (or python-docx)  → Markdown
    chars_per_page < 50           → Docling + OCR (Tesseract / RapidOCR)
    columns == 2 or has tables    → Docling layout model
    otherwise                     → pymupdf4llm (fast path)
validate(markdown):
    sections_found < 3  or  garbage_ratio > 5%  or  ocr_conf < 0.7
        → escalate one level (pymupdf4llm → Docling → VLM)
        → still bad: mark document "needs_review", never index silently

Cleaning after parsing

  • Unicode NFKC normalisation; replace ligatures (ﬁ → fi) and smart quotes.
  • Normalise bullets (•, ▪, ➢, –) to - .
  • Re-join hyphenated line breaks ("micro-\nservices" → "microservices").
  • Drop page headers and footers repeated on every page ("Page 2 of 2", the name repeated at the top).
  • Keep the page number of each block for citations.

Chosen for this use case

  • pymupdf4llm as the fast default: most resumes are digital PDFs.
  • Docling for two-column, table-heavy, DOCX and scanned files (with Tesseract or RapidOCR inside).
  • Qwen2.5-VL via Ollama as an optional last-resort fallback for designed resumes, behind a flag.
  • Validation after every parse; failures go to "needs review", never into the index.
  • Prod swap: the same DocumentParser interface can call Azure Document Intelligence or a resume-parsing API.

The intermediate format: Markdown, JSON, or vectorise directly?

Your sketch asked whether there is a better format than Markdown, or whether to skip formats and vectorise directly. There are five real options. For resumes the answer is to keep two representations side by side.

The options

Direct vectorisation, examined


"Skip parsing and vectorise directly" has three concrete versions.


    

  1. One vector per whole resume. Embed the full text as a single vector. Good for "find resumes similar to this one" or a first-pass ranking against a JD. Bad for questions: one vector averaging Go, payments, mentoring and a degree matches none of them sharply, and you cannot cite a line.
    2. 

  2. Page-image retrieval (ColPali, ColQwen). A vision model embeds each page image as many patch vectors; queries match against patches. Works on designed layouts without any parsing. But you get back a page image, not text: no BM25, no metadata, and the LLM must read the image again to answer. Strong for visually rich documents like slide decks and brochures; overkill for text-first resumes.
    3. 

  3. Embedding raw extracted text in fixed windows. This is still parsing, just bad parsing: you inherit the reading-order problems from chapter 4 without fixing them.
    4. 




Practical use of "direct" vectors.
Keep a whole-resume vector as an extra representation (a "profile vector" of the summary and skills), useful for JD-to-candidate ranking in Phase 2. It complements section chunks; it does not replace them.



Chosen for this use case
    

  • Markdown is the canonical text: it drives section detection, chunking, BM25 and citations.
    • 

  • A JSON profile (chapter 7) is extracted from the Markdown and stored in the metadata DB for filters and exact facts.
    • 

  • Both are saved to disk next to the raw file, so chunking can be re-run without re-parsing.
    • 

  • Switch to page-image retrieval only if a large share of resumes are designed/infographic and parsing keeps failing.

Inside Experience: entries


The Experience section is a list of entries, one per job. Each entry has a header line (title, company, location, dates) and bullets. Detect entry headers with a pattern: a non-bullet line containing a date range (Jan 2021 – Present, 2018–2020, 07/2018 - 12/2020). Entries are the most important retrieval unit in the whole system (chapter 8).



Chosen for this use case
    

  • Parser headings + heuristic detection, mapped with a synonym dictionary (kept in config, easy to extend).
    • 

  • Fuzzy match (string similarity ≥ 0.85) for near-misses.
    • 

  • LLM fallback only when fewer than 3 known sections are found, with a check that every returned section is verbatim text from the input.
    • 

  • Experience split into entries by date-range headers.

Dates and total years of experience


Resume dates come in many forms: "Jan 2021 – Present", "2018-2020", "07/2018 to 12/2020", "Summer 2017". Normalise all to YYYY-MM, with "Present" resolved to the indexing date. Total experience is the union of job intervals, not their sum, because jobs overlap (freelancing during a full-time job, notice periods).


\[\text{YOE} = \frac{1}{12}\Big|\bigcup_{j} [\,s_j,\ e_j\,)\Big|_{\text{months}} \qquad\text{not}\qquad \frac{1}{12}\sum_j (e_j - s_j)\]

Chapter 9 · Chunking


Adaptive min/max token budgets


Your sketch asked: with many uploaded resumes, can the min and max chunk size be set by an algorithm, once, after parsing? Yes. This chapter gives the algorithm, the alternatives, and a live simulator.



Why fixed budgets fit resumes badly


A generic default like "max 512, min 50" ignores the corpus. Resume sections differ wildly: a Certifications section is 30 tokens, a senior engineer's Experience is 900. A batch of graduate resumes has short sections throughout; a batch of principal engineers has long ones. Budgets derived from the actual upload adapt to both.



The algorithm


after parsing all resumes in the batch (or the whole role):
    L = [tokens(section_or_entry) for every resume, every chunkable unit]
    min_tok = clamp(percentile(L, p_low),  64, 128)
    max_tok = clamp(percentile(L, p_high), 256, model_limit - prefix_reserve)
    store {min_tok, max_tok, p_low, p_high, n_units, computed_at} in the index manifest

for each unit:
    if tokens(unit) > max_tok:  split on bullet / sentence boundaries,
                                  repeat the entry header on each part
    if tokens(unit) < min_tok:  merge into the next unit of the same section;
                                  never merge across candidates or across job entries
    else:                        keep whole


\[\text{min\_tok} = \operatorname{clamp}\big(P_{p_{\text{low}}}(L),\ 64,\ 128\big) \qquad \text{max\_tok} = \operatorname{clamp}\big(P_{p_{\text{high}}}(L),\ 256,\ T_{\text{model}} - r\big)\]


Here \(P_p(L)\) is the \(p\)-th percentile of unit lengths, \(T_{\text{model}}\) the embedding model's max tokens, and \(r\) the reserve for the contextual prefix (about 32 tokens). The clamps stop a strange batch from producing absurd budgets. Using \(p_{\text{high}} = 90\) means 90% of units are kept whole and only the longest 10% are split.

Stability matters.
If budgets are recomputed on every upload, the same resume may be chunked differently tomorrow, and old and new chunks no longer match. Compute budgets once per role (or when the corpus grows by more than, say, 50%), store them in the manifest, and re-chunk everything for that role when they change.

Chapter 12 · Indexing


The keyword index: BM25 for skills


Interviewers search for exact things: "Terraform", "CKA", "C#". Dense vectors are bad at rare exact tokens. BM25 is good at them, cheap, and needs no model.



How BM25 scores


\[\text{score}(D, Q) = \sum_{t \in Q} \text{IDF}(t)\cdot \frac{f(t,D)\,(k_1+1)}{f(t,D) + k_1\left(1 - b + b\,\frac{|D|}{\text{avgdl}}\right)}\]


\[\text{IDF}(t) = \ln\!\left(\frac{N - n_t + 0.5}{n_t + 0.5} + 1\right)\]


\(f(t,D)\) is how often term \(t\) appears in chunk \(D\); \(n_t\) is how many chunks contain it; \(N\) is the number of chunks. Rare terms ("Terraform" in 3 of 600 chunks) get high IDF; common ones ("team") get almost none. \(k_1 \approx 1.2\) caps the reward for repeating a term; \(b \approx 0.75\) normalises for chunk length. For resumes, keyword stuffing ("Python Python Python") is limited by \(k_1\) saturation.



The tokenizer is where resumes break BM25


A standard tokenizer lowercases and splits on punctuation. That destroys tech terms: C++ and C# both become c, .NET becomes net, Node.js becomes node + js. Then a search for C# matches every C++ resume.

FAISS versus Elasticsearch, from your sketch


FAISS is a search library: it stores vectors and returns IDs. Text, metadata, filters and keyword search live elsewhere. Elasticsearch/OpenSearch is a search server: one document holds the chunk text, metadata fields, BM25-indexed text and a vector, and one query can combine a keyword match, a kNN search and filters like role_id = r3 AND total_yoe >= 5. That is what "much more context on the DB" means: each hit comes back with everything Phase 2 needs. FAISS + SQLite gives the same result for the assignment with two lookups instead of one.



Index types (why flat is right here)


Exact (flat) search compares the query with every vector. 500 resumes × 12 chunks × 384 dims is 6,000 vectors, about 9 MB, searched in well under a millisecond. Approximate indexes (HNSW, IVF, PQ) only pay off past hundreds of thousands of vectors and cost some recall. Use IndexFlatIP on normalised vectors.

Chapter 14 · Operations


Pipeline engineering and provider interfaces


The difference between an assignment and a system that can go to production is mostly here: re-runs that do not duplicate, versions you can trace, deletes that delete everything, and providers you can swap.



Idempotency and versioning


    

  • Deterministic IDs. doc_id = sha256(file); chunk_id from candidate, section, entry and part. Re-running the pipeline overwrites, never duplicates.
    • 

  • Content hashes. Re-embed a chunk only if its content_hash changed.
    • 

  • Index version. index_version = hash(parser_version, chunker_config, budgets, emb_model). Any change produces a new version; build it alongside the old one, then switch atomically.
    • 

  • Manifest. Every index records how it was built. Phase 2 checks that its query embedding model matches.
    • 




Deletion


A candidate withdraws or asks for their data to be deleted. One function must remove the raw file, Markdown, DB rows, vectors and BM25 entries. FAISS flat indexes support remove_ids (with an IndexIDMap); BM25 indexes are rebuilt for the role. Test it; it is easy to forget one store.



Provider interfaces


Application code imports interfaces only. A factory reads config and returns the concrete class. Swapping free for paid is a config change.
